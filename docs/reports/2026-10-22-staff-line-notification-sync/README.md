# 已綁定 LINE 的同工在通知設定被誤判未綁定

## 原因

LINE 登入身分保存在 Auth；通知設定的 has_line 與實際發送共用 pastoral_staff.line_subject。經由 LINE 申請而建立的同工已有受保護的 app_user_id 對應，但舊帳號同步只填姓名與職稱，沒有填 LINE 通知欄位，因此顯示未綁定且實際發送會回 identity_missing。

## 修復範圍

依現有受保護帳號 UUID 對應，將單一有效 custom:line-web 身分同步到該同工空白的通知欄位。新註冊／核准、稍後附加 LINE 身分，以及變更／移除已同步的 LINE 身分皆由資料庫觸發同步。

不使用姓名、暱稱或 Email 自動判定同一人，不建立或核准帳號連結。原有另外指定的通知身分與已被其他同工使用的 LINE 不被覆寫或挪用。停用帳號不新增綁定，資料有歧義時不選任一個 LINE。

既有已核准 alias 的通知路由與人工指定 LINE 保持既有模式；此修復針對可直接由 app_user_id 找到 LINE 登入身分的新註冊同工。沒有將相同姓名的舊停用帳號併入。

所有 helper／trigger 位於 church_auth，固定空 search_path，撤銷 public、anon、authenticated 的直接執行權。沒有新增對外 RPC、頁面或 Edge Function，不改通知管道、勾選名單、群組與排程，也不發送測試訊息。

## 驗證

- PostgreSQL 實際套用 migration，16 項隔離測試通過，資料全為合成。
- 將本 migration 先套用後，既有帳號／權限原子儲存 44 項及同工申請審核 23 項回歸通過，共 83 項。
- 涵蓋新註冊、先帳號後身分、身分改變／刪除、不同暱稱、同名不相連、停用、既有通知身分、唯一 LINE 衝突、歧義及權限撤銷。
- 正式環境先唯讀檢查，使用者核准後以帶前置雜湊檢查的單一交易套用。已確認原本漏填的有效同工通知欄位與其本人 LINE 登入身分一致；未輸出 LINE ID、Email、電話。交易前後比對通知接收設定及通知管道雜湊，確認勾選名單、群組和管道均保留。正式修復回條存於本機。
- 沒有發送 LINE 測試或變更任何通知接收者。
